# STORY_008 — A stub generation server plays the video job API with scripted outcomes, so no test needs the model

**Epic:** [EPIC_002](../epic/EPIC_002_the_app_has_a_skeleton_a_stub_generation_server_and_a_test_gate.md)
**Status:** Done (2026-09-12, on the Spark)
**Created:** 2026-09-12

As the assistant building the UI, I want a small local server that speaks the exact job API the Spark's adapter will speak — create a job, poll its status, cancel it, fetch its result — and returns outcomes I choose by name, so that every unit, integration and e2e test runs deterministically without the model.

## Current state

No job API exists. The reference's own protocol is an agent session, not a video API ([interactions.md §1](../recon/2026-09-12/interactions.md)); our contract is deliberately create → status → result. STORY_006 (EPIC_004) implements the same contract on the Spark and is written against this document.

## Acceptance Criteria

- [x] **The contract is written before the code**, in `docs/contracts/job-api.md`:
  - `POST /jobs` — JSON `{ prompt, ratio, resolution, durationSeconds }` or multipart with the same fields plus `referenceImage` files (0–2) → `202 { id, status: "queued" }`. Validation errors → `400 { error: { code, message, field? } }`.
  - `GET /jobs/:id` → `200 { id, status, progress, error?, result? }` where `status ∈ queued | running | done | failed | cancelled`, `progress` is 0–100 and never decreases, `error` is `{ code, message }` on `failed` (`code: "moderated"` for a moderated prompt), and `result` on `done` is `{ url, posterUrl, durationSeconds, width, height, sizeBytes }` with `url` = `/jobs/:id/result`.
  - `DELETE /jobs/:id` → `202 { id, status: "cancelled" }`; on an already-terminal job → `409`.
  - `GET /jobs/:id/result` → the video bytes with the right `Content-Type`, `Content-Length` and `Accept-Ranges: bytes` (range requests honoured); `GET /jobs/:id/poster` → an image.
  - `GET /capabilities` → `{ models: [{ id, label }], ratios, resolutions, durationsSeconds: { min, max, step } }` so the UI greys out what the server cannot do from one source of truth.
  - `GET /health` → `200 { ok: true }`. Unknown ids → `404`. Optional `Authorization: Bearer <MODEL_API_KEY>` accepted on every call.
- [x] `tools/stub-generation-server/` is a workspace package (TypeScript, Node's `http` module, no framework) that implements the contract exactly. `pnpm --filter stub-generation-server start` serves on `STUB_PORT` (default 4010); it is also the compose service `stub` (gate image, no published port — reached by service name).
- [x] **Outcomes are chosen by name**, per job, with the `X-Stub-Script` header or `?script=` on `POST /jobs`, and progress advances **per status poll, never by wall clock**, so a test's timing cannot change an outcome. Scripts: `done-after-3-polls` (default: queued → running 33 → running 66 → done), `done-after-1-poll`, `slow-done-after-10-polls`, `fails-after-2-polls` (`error.code: "generation_failed"`), `moderated` (failed on the first poll, `error.code: "moderated"`), `cancel-midway` (stays `running` until `DELETE`), `rejects-upload` (`400` on any job with a reference image).
- [x] Test hooks under `/__stub/`: `POST /__stub/reset` forgets every job; `GET /__stub/jobs/:id/received` returns what the job was sent (`prompt`, `ratio`, `resolution`, `durationSeconds`, `script`, and for each upload its `filename`, `size` and `sha256`); `GET /__stub/jobs` lists ids and statuses so a spec can assert nothing is left running.
- [x] Fixtures in `tools/stub-generation-server/fixtures/`: `fixture.mp4` (H.264 + AAC, ≤ 200 KB, 2 s, 320×180) **and** `fixture.webm` (VP9 + Opus, same content) generated by an `ffmpeg` command recorded in `fixtures/README.md`; `fixture-poster.png` (320×180) and `fixture-reference.png` (a 512×512 image for upload specs). The stub serves the fixture named by `STUB_FIXTURE` (`mp4` default until STORY_010's codec probe records which one both test browsers play; then that one becomes the default). These paths are the only videos allowed in git (`.gitignore` already excepts `tools/**/fixtures/*.mp4|*.webm`).
- [x] The `result` reported by the stub matches the fixture it serves (`durationSeconds`, `width`, `height`, `sizeBytes` read from the file at startup, not hard-coded).

## Technical Notes

- Zero runtime dependencies: `node:http`, `node:crypto` (sha256), `node:fs`. Multipart parsing is a small hand-written parser for the fields above (bounded size, 10 MB per file), unit-tested; if that proves brittle, `busboy` is the one dependency allowed.
- The job store is in-memory; `reset` empties it. Ids are UUIDs.
- The stub is also what the adapter's tests (STORY_006) compare against: the contract document is the single source; changes to it are a new story on both sides.
- Keep the scripts table in one file (`src/scripts.ts`) as data, so a new outcome is a row, not a branch.

## Testing Plan

- **Unit** — `tools/stub-generation-server/src/scripts.test.ts`: for every script, the pure function `(script, pollCount) → { status, progress, error? }` yields the documented sequence (e.g. `done-after-3-polls` returns queued/0, running/33, running/66, done/100 on polls 0–3 and stays done); progress never decreases; unknown script name is rejected. `src/multipart.test.ts`: fields and two files parsed from a real boundary; oversize file rejected; malformed body rejected.
- **Integration** — `tools/stub-generation-server/src/server.test.ts` (Vitest, starts the server in-process on port 0): `POST /jobs` returns 202 and an id; polling `GET /jobs/:id` walks the default script; `fails-after-2-polls` ends `failed` with the code; `moderated` ends `failed` with `code: "moderated"` on the first poll; `cancel-midway` stays `running` across 5 polls until `DELETE`, then `cancelled`, and a second `DELETE` is 409; `GET /jobs/:id/result` bytes equal the fixture file, with the content type and a working `Range: bytes=0-99` request; `rejects-upload` returns 400 for a multipart job with an image; a multipart job's upload is recorded with the right `sha256`; `reset` makes the id 404; `/capabilities` and `/health` shapes; validation: missing prompt 400, bad ratio 400, duration out of range 400.
- **E2E** — N/A: no UI. STORY_010's fixtures use the scripts by name and its specs are the stub's e2e cover from then on.
