# STORY_045 — A video can be extended past 30 seconds because the join happens outside the graph

**Epic:** [EPIC_008](../epic/EPIC_008_a_whole_video_from_one_send.md) — the second story; the Spark side of the owner's one-minute video
**Status:** Proposed (2026-09-15 17:55 EDT — drafted for the owner's approval; no code until he says so)
**Created:** 2026-09-15

As the owner, I want an extension to cost the Spark the same memory whether the clip it continues is 10 s or 60 s long, so that a six-script chain — about a minute of video — runs to the end instead of being refused after the third segment.

## Current state (read from the code and the README's measured split, 2026-09-15)

- **The graph loads the whole source** (`spark/adapter/src/mapping.ts`, the extension branch): `source_video` = `LoadVideo` of the source file, `source_parts` = `GetVideoComponents` — every frame of the source decoded into the graph — from which `tail_frames` takes the last O frames (`ImageFromBatch(source_parts, S − O, O)`) and `tail_audio` the last O frames of sound. The model then generates L = `extensionLength(added, O)` frames (294 for +10 s at overlap 39) with the tail written over the first O.
- **The join is in the graph too:** `joined_frames` = `ImageBatch(source_parts, new_frames)`, `joined_audio` = `AudioConcat`, and `CreateVideo` / `SaveVideo` write the whole joined clip; the shot-change node measures the joined frames; the poster is joined frame 0.
- **The cost is the source's length, not the generation's.** A decoded 1344×768 frame is ≈ 12.4 MB, and the join holds the source once in `source_parts`, again in the batch and again in the node that measures it: the README's split records **87.8–88.7 GiB** for +10 s on a 10 s source and **96.7 GiB** on a 20.75 s source (+8.9 GiB for 255 more source frames — ≈ 35 MB a frame across the copies), against **68.0 GiB** for a fresh 10 s clip. On a 63 s source (1518 frames) the same arithmetic passes the box's 121 GiB. That is the whole reason for `maxSourceSeconds: 30` (`capabilities.ts`; the 400 `unsupported_option` "the video is 31 s long; the Spark extends videos up to 30 s" at `server.ts` › the `continueFrom` check).
- **What the model actually needs of the source is its last 1.6 s.** The tail encode and the masked canvas use O frames; nothing in the sampling touches the other S − O.
- **The adapter already runs ffmpeg** (STORY_034, `watermark.ts` — Debian's ffmpeg in the image, the call injectable for tests), writes to its own volume (`/comfy/adapter`, `spark/comfyui/compose.yaml`; ComfyUI's output is mounted **read-only** to it), and sends files into ComfyUI's input directory through `POST /upload/image` (`comfy.ts` › `uploadImage`, the reference images' path). `result.frames` / `durationSeconds` come from the arithmetic (`framesOf`), not from the file.

## Acceptance Criteria

- [ ] **Only the tail enters the graph.** Before submitting an extension the adapter cuts the source's last O frames and their sound into a short file with ffmpeg (an exact O frames — a frame-index select, not a time seek — and the matching `atrim`), uploads it to ComfyUI's input directory the way a reference image goes, and the graph loads **that file**: `tail_frames` and `tail_audio` are all of it; no node reads the source itself. The tail file is removed from the input directory when the job ends, whatever the outcome.
- [ ] **Only the new part leaves the graph.** The graph saves the frames after the overlap and their sound (`new_frames`, `new_audio` — L − O frames) as the job's ComfyUI output; the poster node is dropped from the extension graph (see the join). The peak of an extension is therefore a fresh L-frame generation plus O frames of tail, whatever the source's length — the README's memory split is re-derived in this story's Done note from the measurement, expected ≈ 70–72 GiB for +10 s (a 294-frame decode against the 243-frame clip's 68.0).
- [ ] **The join is ffmpeg's.** When ComfyUI reports the segment done, the adapter concatenates source + segment (`-f concat`, a stream copy: both files are its own `SaveVideo` output with the same codec parameters, checked by ffprobe before the copy is trusted; the seam falls on a file boundary and the segment's first frame is a keyframe) into its own volume, `/comfy/adapter/joined/<jobId>.mp4`; the job is `done` only when the joined file exists and ffprobe's frame count equals `framesOf(job)` (a mismatch fails the job with a message naming both numbers — never a wrong length). `GET /jobs/:id/result` serves the joined file with ranges as today; the download watermark reads it; `result.poster` is the source's poster (joined frame 0 is the source's frame 0). If a stream copy is not clean at the seam (an audio gap the ear can hear, a timestamp discontinuity ffprobe reports), the sound alone is re-encoded — decided by the measurement and written down.
- [ ] **A joined clip is a source like any other.** `continueFrom` resolves the source's file whether it sits in ComfyUI's output (a fresh clip) or in the adapter's joined directory (an extension); the tail is cut from that file; a chain's fourth segment continues the third's joined file.
- [ ] **The seam is still measured.** The shot-change node runs over `ImageBatch(tail_frames, new_frames)` so the seam is inside what it measures; every reported frame is offset by S − O into the joined timeline before it reaches `result.cuts` (the task page's "The shot changed at 00:11" stays true; `cuts.ts` untouched, the offset applied where the history is read).
- [ ] **The cap rises.** `maxSourceSeconds` becomes **120** (the message keeps its shape); the Done note records the longest source actually extended and its peak, and the README's split says what the number rests on. Disk is the only cost that grows with the source (≈ 0.2 MB a second at the measured bit rates).
- [ ] **Nothing changes for a fresh clip**, for cancel, or for the job-API contract ([docs/contracts/job-api.md](../contracts/job-api.md) — the fields are the same; the contract's note on `maxSourceSeconds` is updated); the adapter's version is bumped; `spark/comfyui/verify.sh` passes.

## Technical Notes

- `mapping.ts`: the extension branch takes `continuation.tailFile` (an input-directory name) instead of the source's output file; `tail_frames` = `GetVideoComponents(LoadVideo(tail))` whole; the join, `joined_*`, the poster and the source nodes go; `video.inputs.images` = `new_frames`, `audio` = `new_audio`; `changes.inputs.images` = `ImageBatch(tail_frames, new_frames)`.
- `tail.ts` (new): `tailArgs(source, out, S, O)` — `-i source -vf select='gte(n,S−O)' -fps_mode passthrough -af atrim=start=(S−O)/24 -frames:v O …`; `concatArgs(list, out)`; `probeFrames(file)`; a runner type injectable like `WatermarkRunner`; the list file and the joined file under `JOINED_DIR` (default `joined/` beside the store, like `watermarked/`).
- `server.ts`: the `continueFrom` check resolves the source through `resultFile(job)` (output dir or joined dir); before `submitPrompt` the tail is cut and uploaded (`uploadImage` accepts any file; the name `tail-<jobId>.mp4`); on ComfyUI's success the join runs before the job is marked done (a failing join fails the job with ffmpeg's message); the cuts offset at the point the node's history is read (`cutsOf(changes, S − O)`); the tail file deleted through ComfyUI's input path (the adapter's input mount, or a `rm` through the upload directory — decided by what the compose file mounts, read then); `result.video` records `{ filename, subfolder: "joined" }` with a root marker the result and poster routes understand; the poster reference copied from the source.
- `capabilities.ts`: `maxSourceSeconds: 120`. `spark/README.md`: the join and the directories. `README.md` › Running the Model: the split re-derived, the measured row.
- Coordination: the adapter is rebuilt and restarted on the Spark (`spark/comfyui/compose.yaml` › `adapter`); never while a job is open (`/health` › `openJobs 0`), the peer session `minimax-db` told before and after.
