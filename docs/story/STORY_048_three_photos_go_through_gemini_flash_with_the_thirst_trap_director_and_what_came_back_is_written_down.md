## Acceptance Criteria

- [ ] **`lib/vertex.ts`** (app, pure apart from `fetch` and `node:crypto`, every network call through an injected `fetch`): `serviceAccountToken(key, { tokenUrl, fetch, now })` builds the RS256 JWT (`iss` = the key's `client_email`, `scope` = the cloud-platform scope, `aud` = the key's `token_uri`, `iat`/`exp` one hour) and exchanges it for `{ accessToken, expiresAt }`; `listPublisherModels(config, token, fetch)` returns the Gemini models the project's region offers, name and display name; `generateContent(config, token, request, fetch, signal?)` posts to the model's `generateContent` endpoint under `VERTEX_BASE_URL` (the real host by default — the exact URL and body shape **read from the Vertex docs the day this is built and copied into the module's header with the date**) with a system instruction, an ordered list of parts (text, or inline image data with its MIME type), the safety settings and the generation config it is given, and returns `{ kind: "reply", text, finishReason, usage: { promptTokens, candidateTokens, totalTokens } }`, `{ kind: "refusal", finishReason, message }` for a candidate stopped for safety or a prompt blocked before generation (the model's own words when it gave any, else the block reason), or `{ kind: "error", status, message }` for an HTTP failure — the response body's error message kept, never the URL or the token. The key file is read once by the caller; nothing in the module logs.

## Technical Notes

- `lib/vertex.ts`: `signJwt(claims, privateKeyPem)` with `createSign("RSA-SHA256")` over `base64url(header).base64url(claims)`; the token exchange is a `POST` of `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer&assertion=<jwt>` as a form body; the expiry is kept so STORY_049 can cache the token in memory until a minute before it lapses. Types for the key file (`client_email`, `private_key`, `token_uri`) and the authorized-user shape 047 named as the fallback (`refresh_token`, `client_id`, `client_secret` → a refresh-token exchange at the same endpoint); `readKeyFile(path)` tells the two apart.
- `lib/agent-request.ts`: `readSkill(dir)` → `{ id, name, description, metadata, body, references: [{ file, text }] }` (frontmatter parsed by hand — three keys and a nested map; no YAML library); `assembleRequest(skill, image: { bytes, mimeType }, notes, instructions = [])` → `{ systemInstruction, parts }` with the order fixed here and reused by 049 and 052.
- The request's `generationConfig` (temperature, max output tokens) and `safetySettings` are constants the spike names and the Done note records; 049 imports them.
- `VERTEX_BASE_URL` (default the real regional host, read from the docs) and `VERTEX_TOKEN_URL` (default the key's `token_uri`) are read by `readAgentConfig()` so the stub can stand in for both in 049; documented in `.env.example` as gate-only knobs.
- The spike runs in the gate container so nothing is installed on the box: `docker compose run --rm gate pnpm --filter app agent:spike …` with the key volume; the photos are read from their paths on the bind-mounted repo (`test/…`, untracked) and from `spark/data/input/` (a second bind mount for the run, read-only).
- Google's price list and the Vertex request docs are read the day this is built (CLAUDE.md § 3.8's rule for live state); the module header and the Done note carry the URLs and the date.
