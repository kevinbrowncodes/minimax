## Acceptance Criteria

- [ ] **A `gcloud` service in the root `compose.yaml`** on the `tools` profile: Google's official `google-cloud-cli` image (the `slim` variant, pinned to the version read from the registry that day), `spark/data/gcloud/` bind-mounted as its configuration directory (so the login persists across runs and stays gitignored) and `spark/data/secrets/` as `/secrets`; runs as the owner's uid like the stub. `spark/gcloud/login.sh` (host wrapper, shellchecked by `spark/comfyui/lint.sh`'s pattern) runs `gcloud auth login --no-launch-browser` interactively — **the owner runs it in his own terminal**, approves the URL in his browser and pastes the code there; the assistant never runs it and the code never appears in the chat. `spark/gcloud/status.sh` prints whether a login exists (`gcloud auth list` filtered to the account's presence: "signed in: yes/no" and the project the config is set to — never a token).
- [ ] **`spark/gcloud/setup-vertex.sh <project-id> <billing-account-id> [region]`** runs from that session (the assistant runs it) and is idempotent: creates the project (a fresh one — the owner's decision) with the name *MiniMax Local*, links the billing account, enables `aiplatform.googleapis.com`, **checks the effective `iam.disableServiceAccountKeyCreation` policy first** (a fresh personal project has no organisation, so it cannot be enforced; if it is, the script stops and names the fallback below), creates the service account `minimax-agent` with **`roles/aiplatform.user` only**, writes its key to `/secrets/vertex-sa.json` (mode 600, owned by the owner's uid), and writes `VERTEX_PROJECT` and `VERTEX_LOCATION` into the gitignored `.env` (creating it from `.env.example` if absent, updating in place if present). Its output names each step and **prints presence, never content**: "key written: yes". The fallback if keys are blocked: `gcloud auth application-default login` by the owner, the ADC file copied to the same path, and the app's config accepts either shape (a service-account key or an authorized-user file) — decided and written down in the Done note if it was needed.
- [ ] **The app container mounts the key read-only and knows the three variables.** `compose.yaml` › `app`: `./spark/data/secrets:/secrets:ro`, `GOOGLE_APPLICATION_CREDENTIALS=/secrets/vertex-sa.json`, `VERTEX_PROJECT`, `VERTEX_LOCATION` (default `us-central1`) and `VERTEX_MODEL` from `.env`; `.env.example` documents all four with one line each and says the photos and notes go to Google. `lib/agent-config.ts` › `readAgentConfig()` returns `{ configured: true, project, location, model, keyFile }` or `{ configured: false, reason }` — the reason names the missing thing (`VERTEX_PROJECT is not set`, `the key file is not mounted at /secrets/vertex-sa.json`, `VERTEX_MODEL is not set — STORY_048's spike pins it`) and never a value or a path outside the container. The three variables are read from the env store first (`envValue`, so Settings › Environment variables can override — the model id is the one likely to change) and `process.env` second.
- [ ] **`GET /api/capabilities` gains `agent: { configured: boolean, reason?: string }`**, merged by the app into the adapter's JSON (the adapter is untouched; the stub is untouched); `reason` only when `configured` is false. After this story alone it reads `configured: false, reason: "VERTEX_MODEL is not set — …"` on the Spark until 048 pins the model — expected, and the Done note says so.
- [ ] **Nothing secret is in git and nothing can get there by accident:** a unit test asserts `.gitignore` covers `spark/data/`, `.env` and `.env.*` (the guard for the key, the `gcloud` directory and the variables); `git status --short` before the commit shows none of `spark/data/secrets`, `spark/data/gcloud` or `.env`; the README's new **Agent mode** section names the four variables, the mount, the two scripts, the login rule and that the photos go to Google, and the Spark README's scripts table gains the two scripts.
- [ ] **The credential works, proven without printing it:** from the `gcloud` container with the service account activated from the key (`gcloud auth activate-service-account --key-file /secrets/vertex-sa.json`), a request with its access token to Vertex's publisher-models list for the region returns 200 and the count of Gemini models (the names go to the Done note; the token is used in the command and never echoed); the app container sees the file (`docker exec minimax-app test -r /secrets/vertex-sa.json && echo mounted: yes`).

## Technical Notes

- `compose.yaml`: the `gcloud` service (`image: gcr.io/google.com/cloudsdktool/google-cloud-cli:<pinned>-slim`, `profiles: ["tools"]`, `user: "${SPARK_UID:-1000}:${SPARK_GID:-1000}"`, `volumes: ./spark/data/gcloud:/gcloud-config`, `./spark/data/secrets:/secrets`, `environment: CLOUDSDK_CONFIG=/gcloud-config`, `entrypoint: gcloud`); the `app` service's mount and the four variables. `spark/gcloud/lib.sh` shares the compose wrapper's shape with `spark/comfyui/lib.sh`; `login.sh` uses `docker compose run --rm -it gcloud auth login --no-launch-browser`; `setup-vertex.sh` chains `projects create`, `billing projects link`, `services enable`, `resource-manager org-policies describe iam.disableServiceAccountKeyCreation --effective`, `iam service-accounts create`, `projects add-iam-policy-binding`, `iam service-accounts keys create`, each guarded by a "does it exist already" check so a re-run is safe; `chmod 600` on the key; the `.env` edit with `sed -i` on existing keys or an append.
- The billing account id is an identifier, not a credential; the owner reads it from the console and passes it on the command line (the script does not list accounts, so nothing of his billing shows in a transcript beyond the id he chose to give).
- `app/lib/agent-config.ts` (pure, `env` and a `readValue` injected for tests); `app/app/api/capabilities/route.ts`: relay, parse, merge `agent`, re-serialise — a non-JSON upstream answer is relayed as today without the field.
- Region: the owner chose a fresh project; the region defaults to `us-central1` (the review's recommendation) unless he names another when he gives the id.
- Nothing installed on the host; the only host-side files are the two thin wrappers and `lib.sh`.
